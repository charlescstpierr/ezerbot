# Vérification arm64 bornée — helper original 0.70.2

La limite « seulement x86_64 » est levée pour les six propriétés ci-dessous : branchement du callback, vidange du permis, posts de relâchement, contrôle avant mouse-down, prédicat d’admission de session et branches d’échec du relâchement. Les corps arm64 de l’original **Grok Bot 0.70.2** confirment ces propriétés ciblées. Cela ne démontre ni une équivalence de toutes les fonctions ni un comportement observé en exécution.

L’origine reste `inputs/Grok Bot.app/Contents/Helpers/Grok Bot Computer Use.app/Contents/MacOS/CUGrokBotService`, SHA-256 `94a4a3d6965dd9f759c2fb811450fbe2a2194d14f538a351b945d2142d628b31`. La slice arm64, CPU subtype 0, commence à l’offset universel `0x32c000` et mesure 3 123 536 octets. **9 symboles, 1 196 instructions et 4 784 octets** ont été désassemblés et comparés aux octets de cette slice : **zéro divergence**. Les adresses ci-dessous sont virtuelles, sans ASLR.

Le [ledger](../evidence/native-arm64-residual.json) donne chaque symbole, commande exacte, offset universel, hash de corps et fichier, ainsi que 87 ancres avec lignes et extraits. Les preuves x86_64 sont réutilisées par leurs empreintes; aucun ancien rapport ou index n’est modifié. Le [vérificateur hors ligne](../evidence/native-arm64-residual-verify.py) fonctionne avec la bibliothèque standard Python et ne lance pas le helper : `python3 evidence/native-arm64-residual-verify.py`. Son option `--redisassemble` relance uniquement les neuf commandes `llvm-objdump` enregistrées.

1. **Le callback possède le même branchement ciblé.** Le couple `ADRP/ADD` à `0x10000f9b0–0x10000f9b4` matérialise `0x10000e764`; `STP x8,xzr,[x22,#0x88]` écrit la fonction et un contexte nul aux offsets `+0x88/+0x90`. Le lease est fourni au service RPC à `0x10000fa14`. Dans `revokeLocked`, `LDP x24,x23,[x19,#0x88]` relit ce couple; le code appelle `permit.revoke`, garde le Set retourné dans `x0`, place le contexte dans `x20`, puis fait `BLR x24` à `0x10007c7e4`. L’appel du couple `onStopped` à `+0x78` vient ensuite. Sources : [montage](../evidence/native-arm64-residual-app_setup.asm.txt), [révocation du lease](../evidence/native-arm64-residual-lease_revoke_locked.asm.txt). Ledger : `NAR-01`.

2. **La vidange est reconstruite indépendamment sur arm64.** Le wrapper charge le verrou à `permit+0x10`, le prend, appelle la fermeture verrouillée, déverrouille, puis invoque les handlers. La fermeture exige le tag `+0x18 == 2`, écrit la raison de révocation, vide les handlers `+0x20`, lit le Set à `+0x28` à `0x10007bf68` et le remplace par le Set vide à `0x10007bf6c`. Le tuple handlers/Set est écrit dans le tampon fourni par l’appelant. La branche déjà révoquée fournit des collections vides. Le sens des registres est suivi dans ces appels arm64 : le tampon résultat est placé dans `x8`, sans transposer la convention x86_64. Sources : [wrapper](../evidence/native-arm64-residual-permit_revoke.asm.txt), [vidange](../evidence/native-arm64-residual-permit_revoke_locked.asm.txt). Ledger : `NAR-02`.

3. **Le relâchement appelle concrètement CoreGraphics.** La fermeture crée une source de state 1 puis appelle directement `releaseHeldInputs` à `0x10000e7b0`. Les posts souris, clavier et modificateurs sont à `0x100080a0c`, `0x100080af4` et `0x100080bf8`; chacun prépare `w0=0`, le tap HID. Le chemin souris lit `[2,4,26]` à `0x10012f6d0`, soit left-up/right-up/other-up. Le clavier prépare le keycode sur 16 bits et `keyDown=false`, conserve le masque `0x1e0000`, puis appelle les transitions des modificateurs et poste celles du résultat `up` sous type `flagsChanged=12`. Les tables arm64 up et down ont été lues dans l’original et valent respectivement `[2,4,26]` et `[1,3,25]`. Les destinations des `BL` vers la révocation et le poster, ainsi que les adresses matérialisées du callback et des tables, ont aussi été décodées depuis les mots machine. Sources : [fermeture](../evidence/native-arm64-residual-release_callback.asm.txt), [posts de libération](../evidence/native-arm64-residual-release_inputs.asm.txt). Ledger : `NAR-03`, `constants`, `direct_branch_checks`, `address_materialization_checks`.

4. **Le permis est contrôlé avant une action souris réelle.** `requiredPermit` refuse un pointeur absent, prend le verrou `+0x10`, exige le tag `+0x18 == 2`, contrôle l’annulation puis déverrouille. Indépendamment de ce précontrôle, `mouseDown` retrouve le verrou depuis son argument de permis, vérifie tag et annulation, puis crée et poste le down à `0x100081b8c`. L’accès au Set `+0x28` et son insertion viennent avant le déverrouillage normal. La révocation qui prend le même verrou ne peut s’intercaler entre cet appel au post et son inscription sur cette branche. Les appelants arm64 du service et toutes les autres actions ne sont pas reconstruits ici. Sources : [requiredPermit](../evidence/native-arm64-residual-required_permit.asm.txt), [mouseDown](../evidence/native-arm64-residual-mouse_down.asm.txt). Ledger : `NAR-04`.

5. **Le prédicat d’admission garde les tests de session et d’état prêt.** Le corps `admit(sessionID:)` compare d’abord l’ID demandé à la paire de chaîne `+0x58/+0x60`. Son autre branche exige un enregistrement actif (`+0x20` non nul), teste le bit à `+0x40`, compare l’ID actif `+0x18/+0x20`, puis conserve le permis à `+0x38`. Les noms de champs suivent l’interprétation déjà reconstruite sur x86_64 et les accès visibles; les noms de variantes d’enum ne sont pas déduits des seuls tags immédiats 0/1/2. Cette admission concerne la session de contrôle; les politiques de peer, d’UID et de signature du socket ne font pas partie de l’échantillon arm64. Source : [admission de session](../evidence/native-arm64-residual-lease_admit_locked.asm.txt). Ledger : `NAR-05`.

6. **Les échecs de création de relâchement restent des sorties sans nouvelle tentative visible.** Un key-up nul saute vers l’itération suivante à `0x100080a30`; une transition modifier-up nulle est sautée à `0x100080b3c`; le chemin d’échec mouse-up revient à la boucle à `0x100080c80`. Aucune réinsertion ni nouvelle tentative n’apparaît dans ce corps, alors que le Set du permis a déjà été vidé. Ce constat confirme ces branches arm64 précises. Le scénario x86_64 de modifier-down partiellement posté avant inscription, dans `postKey`, n’a pas été réétudié sur arm64. Source : [branches de libération](../evidence/native-arm64-residual-release_inputs.asm.txt). Ledger : `NAR-06`.

La comparaison porte sur des propriétés d’appels, de branches et d’état sélectionnées, avec une certitude statique élevée; elle ne constitue pas une preuve formelle d’équivalence. L’échantillon ne couvre pas les 29 corps x86_64 précédents, les politiques du socket, la chaîne entière de dispatch, la tenue clavier, la frappe Unicode ni le corps arm64 du constructeur de transitions. L’activation par le daemon, les permissions macOS, la livraison des événements et la latence d’annulation restent inconnues. Aucun code 0.71, runtime, compte, réseau, prompt OS, installation ou modification de binaire n’a participé à cette vérification de l’original 0.70.2.
